# GVYA Agent Rules

## Architecture

- **Clean break by default.** GVYA does not preserve backward compatibility unless the user explicitly changes this rule. If a better architecture requires changing a source contract, persisted shape, API, workspace version, artifact contract, or implementation boundary, change it cleanly and update all callers, tests, validation, and documentation. Do not add compatibility shims, migration aliases, dual readers/writers, deprecated fields, or fallback behavior merely to preserve an earlier development shape.
- **All pre-publication contracts stay at v1.** GVYA is not published yet, so source, artifact, program, runtime wire, Engine asset, authoring-policy, and similar format contracts remain version `1` and are updated in place by clean break. Do not increment a format version during active development and do not add backward readers or migrations.
- Keep compiler/runtime semantic authority canonical and deterministic. Do not create JavaScript semantic/compiler/runtime fallbacks.
- Keep the kernel language-neutral by default. Language/transliteration profiles belong in explicit package data; do not add built-in language profiles or ambient lexical assumptions.
- Treat canonical GVYA source plus the Rust CLI as the machine-authoring interface. External agents may author source directly; do not add model/provider registries, credentials, prompt/session protocols, or a model-hosting agent runtime to Studio or the GVYA source contract. A deterministic CLI authoring-loop decision may coordinate existing canonical gates, but it must not duplicate their semantics or mutate the accepted baseline. External agent hosts consume `gvya.cli.author-step/1` and embedded `gvya.cli.check-change/1` directly; Studio remains the human editor and must not mirror those machine reports, classify mechanics, infer acceptance, edit the candidate on behalf of a model, or persist provider/session state.


## Development speed and validation discipline

- **Reason first; validate only the changed boundary.** Active development is not a release ceremony. Before running anything, identify which files/contracts can actually be affected. Run the smallest check that can falsify the change. Do not routinely run umbrella suites, browser acceptance, AI fuzz, Rust workspace tests, Engine acceptance, source-manifest validation, fresh extraction, or packaging after a scoped edit.
- **Target a sub-three-minute normal loop.** A small Studio/UI/model task should normally finish in roughly a few minutes, not tens of minutes. If validation is dominating a small change, stop and narrow the validation scope instead of adding more ritual checks. This is a workflow target, not permission to skip a directly relevant correctness check.
- **Validation is staged.** During an edit: inspect -> edit -> type-check/compile only if the language changed -> run the one or two directly relevant contract tests -> stop. Run broad/full validation only once when explicitly closing a baseline/milestone, when the owner asks for it, or when the changed boundary genuinely spans the repository. Do not repeat a full pass after each sub-fix.
- **Do not rebuild stable Engine assets unless Engine source/ABI semantics changed.** Studio UI, package authoring data, package history, navigation, labels, CSS, and ordinary source-model edits do not justify rebuilding Engine WASM unless they change the compiler/runtime executable contract. Bot/Package content never triggers Engine rebuild.
- **Do not package during iteration.** ZIP creation, manifest refresh, fresh-extraction proof, release-gate checks, and delivery handoff generation happen when a baseline is being closed, not after every edit. Work in the existing extracted workspace until that point.
- **Do not add regression tests for cosmetic detail by default.** Add or extend a permanent test only for a durable contract, data/safety invariant, architectural boundary, or regression expensive to rediscover. Labels, spacing, ordinary CSS, and simple presentation changes normally need inspection/type-check only. Delete temporary probes and scratch scripts before the task ends.
- **Use exact tests, not umbrella scripts, during iteration.** Examples: Studio model/navigation mutation -> `node validation/studio-contract.mjs`; human editor behavior -> `node validation/human-authoring-contract.mjs`; Engine browser bridge -> `node validation/studio-engine-contract.mjs`; SDK -> `node validation/runtime-sdk-contract.mjs`. `npm run test:source`, full Cargo workspace tests, `engine:accept:v1`, `validation/authoring-e2e/run.mjs`, browser acceptance, and certification commands are milestone/final gates unless the change directly spans them.
- **Author and validate vertical conversation slices.** When an accepted source snapshot exists, keep it immutable and validate each ordinary candidate source slice with `gvya check-change BASE CANDIDATE --json` rather than rerunning the entire growing authored suite after every small batch. The gate compares composed GVYA semantics, derives required mechanic proof per source subject, runs every changed test plus conservative old/new blast-radius, semantic-neighbor and bounded sentinel tests, and escalates global/unbounded changes to the full suite. Every required mechanic must be directly covered by an added/modified **manual, non-generated** Regression Case or Conversation Scenario; one proof test may cover several mechanics only when its expectations actually observe them. Generated, unrelated, neighbor-only, sentinel or unchanged historical tests do not satisfy missing mechanic proof. Treat `gvya.cli.check-change/1` and its `impact.mechanic_coverage` as acceptance authority; do not reproduce this policy in an agent prompt or another tool. External agents should use `gvya author-step BASE CANDIDATE --json` when they need a deterministic repair/promote decision: it reuses the same gate and may emit candidate-source, build, runtime, missing-mechanic, failing-test, rerun, or promotion actions. The accepted BASE stays immutable until promotion. Promote a candidate only after the gate accepts it, then use that promoted source as the next baseline. `gvya check` / `gvya test` remain checkpoint/final gates.
- **Use structural patterns for explicit shape, samples for semantic evidence.** Meaning `patterns` are deterministic whole-utterance author rules and run before semantic scoring; do not imitate a structural rule by stuffing near-duplicate samples or by changing scorer thresholds. Keep structural rules anchored by at least one literal or Matcher Profile set, use named captures only for declared String slots, and treat `pattern_sets` as transparent Matcher Profile data. Language Profiles own normalization, morphology and lexical policy. Because either profile can affect distant utterances, structural-pattern, Matcher Profile and Language Profile changes must force the full authoring suite.
- **Precision before coverage when authoring matcher evidence.** For every new or materially changed Meaning, write at least one close-boundary/confounder case before adding broad samples. Exact contiguous authored samples remain eligible evidence inside longer utterances, and the generic matcher gives otherwise-comparable shorter samples more lexical priority than longer samples; this is not Social-only behavior. Language Profile ambiguity/direct-cue data may still bound or strengthen a one-word sample without consulting MeaningClass. Short/generic evidence (`right`, `back`, `continue`, `meaning`, `runtime`, `چی`, and similar) is therefore high-impact: prove the intended embedded case and its nearest confounder, and use authored negatives/profile weighting when a collision must be suppressed instead of adding a hidden class-specific hard drop.
- **Tune repair from two corpora, never by feel.** A repair-floor change must be justified against both useful near-misses/typos and clearly unrelated off-domain utterances. Preserve useful repair while forcing low-credibility candidates to fallback; do not use repair as a second fuzzy matcher.
- **Authored prompts must be truthful and recovery must be varied.** If a response says “ask me why”, “want the workflow?”, “say architecture”, “another one”, or offers any other continuation, add a Scenario proving that continuation really resolves. Repeat/fallback paths should use intentional stages and multiple equally-correct response variants where repetition would otherwise sound robotic.
- **Close conversational authoring with a quality gate, not only mechanic proof.** Before freezing a Bot, run domain-noun smoke, close-boundary/confounder checks, obvious off-domain precision, typo/near-miss checks, repeat/fallback recovery, promised-follow-up sessions, multilingual parity, and a mixed roughly twenty-turn adversarial conversation. Keep these quality probes held out from positive samples. The canonical recipe in `docs/PACKAGE_AUTHORING_RECIPE.md` owns the detailed procedure.
- **One path per task.** Reuse the existing canonical helper/model/validator and remove superseded paths when a contract changes. Do not create parallel registries, duplicate inventories, alternate mutation paths, or new test harnesses when an existing path already owns the job.
- **Object authoring modals are transactional.** Opening New/Edit, typing, toggling, adding nested rows, or closing/canceling a modal must not mutate canonical Studio source. Keep a local draft, show validation inside the owning modal, and commit exactly once only after the author presses Save/Create and blocking validation passes. Do not insert placeholder Behaviors, Capabilities, Assets, Localizations, tests, scenarios, or other authored objects merely because an Add/New button was pressed. Explicit destructive actions (Delete/Restore) and ordinary immediate Settings values are separate contracts.
- **Inspect live contracts, not the whole repository from memory.** For a scoped request, open the exact owning files/contracts first. Do not re-audit unrelated architecture, re-open references, or broad-search the tree unless the local contract is genuinely ambiguous or the requested change crosses that boundary.
- **No speculative cleanup while fixing a scoped issue.** Do not opportunistically refactor adjacent code, redesign contracts, add abstractions, or audit unrelated areas unless the requested fix exposes a real boundary defect. If the scope grows, checkpoint the requested fix first.
- **Stop heavy processes.** Do not leave watchers, dev servers, Cargo builds, browser runners, or background processes alive after the relevant check.

## Rust warning policy

- Rust workspace code must compile without default rustc warnings; workspace crates deny the `warnings` lint group so unused imports, unused variables, dead code and similar signal cannot be buried in build output.
- `missing_docs` is intentionally not enabled as a build warning while GVYA is pre-public-API. Do not generate low-value placeholder rustdoc merely to silence the compiler. Canonical architecture/contracts/docs remain authoritative until a public Rust API documentation gate is explicitly introduced.

## Source hygiene

- Treat historical/reference projects as research only; do not package them into GVYA source.
- Keep iteration reports and delivery handoffs outside the source package unless they are authoritative durable documentation.

## File recovery backups

- **Back up before every existing-file mutation.** Before modifying, overwriting, renaming, or deleting any existing file, copy its current bytes to `_backup/YYYY-MM-DD/<workspace-relative-directory>/<filename>.HHmmssfff.bak`. This creates only one top-level backup directory per day, mirrors the original directory layout, and records the exact backup time on the file itself.
- Files changed as one operation may share the same time suffix. A file changed more than once must receive a fresh pre-change copy with a new suffix; never overwrite an earlier backup. Newly created files have no pre-change copy and do not need placeholder backups.
- `_backup` is recovery-only: never modify its saved copies, include it in source manifests/packages/version control, or recursively back it up. Restore by copying a saved file back to its original path, leaving the backup intact.
- Never delete, prune, or reorganize `_backup` without the user's explicit permission.

## Engine and simulation rule
- Engine WASM belongs to a GVYA Engine version, never to a Bot or Package. Do not rebuild Engine WASM because authored content changed.
- Studio simulation must be zero-setup and source-native: internally compile the selected resolved Bot with the bundled canonical Rust compiler asset and immediately run the transient artifact with the bundled canonical Rust runtime asset.
- Never expose normal human controls for selecting/locating WASM or intermediate `.gvya` files.
- Never add a JavaScript semantic/compiler/runtime fallback. Multiple host edges may wrap the canonical Rust implementation, but may not reproduce its semantics.
- Normal Studio simulate/build/export must not invoke Cargo. Engine assets are built explicitly once per Engine version and then verified/reused/copied.
